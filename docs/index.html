Bausteine

Löst eine Aktion aus. Für Navigation zu einer anderen Seite einen Link verwenden.

Einzeilige Texteingabe mit sichtbarem Label und optionalem Hilfstext.

Auswahl einer unabhängigen Option, die man an- oder abwählen kann.

Schaltet eine Einstellung sofort ein oder aus, ohne Speichern.

Filter zum An- und Abwählen. Mehrere Chips bilden eine Filterzeile.

Kurzer Status oder Kategorie, nicht interaktiv.

Hinweis im Seitenfluss zu Status, Erfolg, Warnung oder Fehler.

Gruppiert zusammengehörige Inhalte mit optionaler Aktion.

Führt zu einer anderen Seite oder Stelle. Für Aktionen einen Button verwenden.

Vollständiges Anmeldeformular aus TextField, Checkbox und Button. Als Ganzes verwenden statt neu zusammenzubauen.

Und die Regeln?

Wofür ein Baustein da ist und was für ihn gilt, steht in specs/rules.json. Jede Regel ist ein Satz mit Begründung.

So sieht der Code aus wie die Vorlage

Drei Messungen. Jede läuft von selbst, bei jeder Änderung.

  1. 1Werte werden nicht abgetippt

    Farben, Abstände, Radien und Schrift kommen aus Figma direkt ins CSS.

  2. 2Jeder Baustein wird nachgemessen

    Ein Programm öffnet jede Variante im Browser und vergleicht Farben und Rahmenstärken mit Figma, hell und dunkel.

  3. 3Jede Seite wird geprüft

    Erfundene Bausteine, feste Farbwerte und feste Abstände fallen auf. Am fertigen Bild werden Handybreite, Kontrast und Klickflächen gemessen.

Was noch nicht gemessen wird

Welchen Abstand, Radius oder Textstil ein Baustein an welcher Stelle nutzt. Die Werte selbst kommen aus Figma, aber ein falsch gewählter Innenabstand fiele heute nicht von selbst auf.

Wenn ein KI-Agent baut

Ein Agent arbeitet in einer festen Schleife. Vier Dinge nehmen ihm dabei das Raten ab.

  1. 1Lesen

    Die erzeugte Liste der Bausteine, Werte und Regeln laden.

  2. 2Bauen

    Nur mit Bausteinen des Systems. Eigenes CSS nur fürs Layout.

  3. 3Prüfen

    Den Check laufen lassen und jeden Befund beheben.

    node cli/fundament.mjs check <Pfad>
  4. 4Am Bild messen

    Handybreite, Kontrast, Klickflächen, Namen.

    node cli/fundament.mjs audit <Pfad>
  5. 5Höchstens drei Runden

    Danach berichten, was offen ist, statt weiter zu raten.

  6. 6Lücken melden

    Fehlt ein Baustein, nicht nachbauen, sondern nennen.

  1. 1
    Er bekommt eine Liste, keine Beschreibung

    Für jeden Baustein steht fest, wie er heißt, welche Einstellungen er hat und welche Werte erlaubt sind. Die Liste wird erzeugt. Niemand tippt sie ab, also veraltet sie nicht.

    fd-button
  variant   primary | secondary | ghost | danger
  size      md | sm
  disabled  ja | nein
  label     Text
  2. 2
    Der Check sagt, was falsch ist und was gilt

    Erfundene Bausteine, falsche Werte, feste Farben und feste Abstände fallen sofort auf. Jede Meldung nennt die Behebung.

    <fd-button variant="blue"> ist kein gültiger Wert.
    Behebung: Erlaubt: primary, secondary, ghost, danger (Standard: primary).

Fester Farbwert #1f4fd8.
    Behebung: Durch ein semantisches Token ersetzen, var(--fd-color-…).
  3. 3
    Regeln haben einen Grund

    Jede Regel ist ein kurzer Satz mit Begründung. Die Begründung hilft dem Agenten in Fällen, an die niemand gedacht hat.

    Regel:  Höchstens ein primärer Button pro Ansicht.
Warum:  Mehrere primäre Aktionen konkurrieren um Aufmerksamkeit.

Eine gute Regel schreiben

Drei Dinge machen eine Regel brauchbar, für Menschen wie für Agenten.

1 / Sie kommt aus einem echten Fehler

Regeln auf Vorrat liest niemand und prüft niemand.

2 / Ein Satz, den man zählen oder zeigen kann

„Höchstens ein primärer Button pro Ansicht“ lässt sich zählen. „Buttons sparsam einsetzen“ lässt sich nur auslegen.

3 / Sie hat ein Warum

Ein Satz, der sagt, wovor die Regel schützt. Damit lassen sich auch Fälle entscheiden, an die niemand gedacht hat.

Beispiel

{
  "id": "card/one-action",
  "text": "Höchstens eine Aktion im Footer.",
  "why": "Karten sind Einstiege, keine Formulare.",
  "check": "max-children"
}

So steht eine Regel in specs/rules.json. Lässt sie sich nicht automatisch prüfen, steht bei check der Wert null.

So nicht

Bedienelemente übersichtlich halten.

So

Höchstens eine Aktion im Footer.

So nicht

Der Fokus muss gut sichtbar sein.

So

Hover und Fokus kommen aus der Komponente, nie selbst gestaltet.

So nicht

Fehlt eine Komponente, improvisiere passend zum Stil.

So

Fehlt eine Komponente, nicht nachbauen. Die Lücke im Bericht nennen.

Ohne Web Components: nur HTML und CSS

Die Bausteine gibt es als Web Components und als reines HTML mit CSS. Beide nutzen dasselbe CSS und dieselben Tokens. Die HTML-Fassung wird aus den Web Components erzeugt und im Browser nachgemessen: Sie sieht gleich aus.

Als Web Component

<fd-button label="Speichern"></fd-button>

Als HTML und CSS

<button class="fd-button" data-variant="primary" data-size="md" type="button">
  <span class="fd-button__label">Speichern</span>
</button>

Die HTML-Fassung jedes Bausteins steht bei der Komponente und unter generated/html/. Eine ganze Seite ohne Web Components: ui/examples/nur-html.html.

Was in beiden Wegen gleich bleibt

Figma als Ort für das Aussehen, die Tokens, die Regeln, der Abgleich zwischen Figma und Code und die Messung im Browser (audit). Die Messung arbeitet am fertigen Bild und gilt deshalb für beide Wege voll.

Was der Check im HTML-Weg nicht sieht

Regeln zu Slots, den Fehlertext im Fehlerzustand und den Grund bei deaktivierten Feldern. Bei Web Components hängen sie an Attributen. Im reinen HTML gibt es dafür keine feste Stelle.

Wann welcher Weg

Web Components sind der Standard. Reines HTML passt, wenn auf der Seite kein Skript laufen soll oder das Markup aus einem System kommt, das eigene Elemente nicht kennt.

Beleg aus der ZDS-Probe

Mit CSS ohne Verhalten haben Agenten jedes Bedienelement selbst gebaut, eigenes Skript geschrieben und Schalter ohne Namen geliefert (probe-zds/ERGEBNIS.md). Die fertigen Vorlagen und check --html verkleinern diese Lücke. Das Verhalten ersetzen sie nicht.

Was man lassen sollte
Namen und Werte in Anleitungen abtippen

Listen von Komponenten oder Tokens in Prompts und Hinweisdateien veralten. Sie stehen nur in der erzeugten Liste.

Regeln, die niemand prüft

Eine Regel ohne Check und ohne Frage im Review steht nur auf dem Papier.

Fehlendes mit Text flicken

Kann ein Baustein etwas nicht, hilft kein Hinweis. Er braucht den Slot, den Zustand oder das Verhalten.

Ausnahmen im Produkt

Ein überschriebener Wert ist eine Regeländerung ohne Entscheidung. Kommt die Ausnahme wieder, fehlt eine Variante.

Alle Regeln

33 Regeln, jede ein Satz mit Begründung. 21 prüft der Check von selbst, die übrigen brauchen ein Urteil.

Für jede Seite

  • Trennung über Fläche und Linie. Keine Verläufe, keine Schlagschatten.

    Verläufe und Schatten haben keine Tokens und brechen im Dark Mode.

    principles/surface-and-line
  • Satzschreibung. Keine Versalien per text-transform.

    Versalien sind schwerer zu lesen und wirken wie Werbung.

    principles/sentence-case
  • Aktionen sagen, was passiert.

    „Mehr erfahren“ oder „Hier klicken“ verraten nicht, was nach dem Klick kommt.

    principles/action-says-what
  • Abstände kommen aus der Skala.

    Zwischenwerte zerstören den Rhythmus und lassen sich nicht gemeinsam ändern.

    principles/spacing-from-scale
  • Bedienelemente kommen aus dem System, keine nackten <button> oder <input>.

    Nur Systemkomponenten bringen Fokus, Zustände und Barrierefreiheit mit.

    principles/system-controls

Je Baustein

Button / 5 Regeln
  • Höchstens ein primärer Button pro Ansicht; ein danger-Button und ConfirmAction zählen als primär.

    Mehrere primäre Aktionen konkurrieren um Aufmerksamkeit.

    button/one-primary
  • Beschriftung beginnt mit einem Verb und nennt das Ergebnis.

    Nutzer:innen wissen vor dem Klick, was passiert.

    button/label-verb
  • Farbe nur über variant, nie eigene Füllungen.

    Sonst brechen Dark Mode und Kontrastgarantie.

    button/no-custom-colors
  • Hover und Fokus kommen aus der Komponente, nie selbst gestaltet.

    Der Fokusring ist eine Zusage an Tastaturnutzer:innen und muss überall gleich aussehen.

    button/states-from-system
  • variant=danger nur für Aktionen, die etwas unwiderruflich löschen oder beenden, und nie als einzige Absicherung.

    Rot warnt, schützt aber nicht vor einem versehentlichen Klick; es braucht zusätzlich eine Bestätigung.

    button/danger-confirm
TextField / 4 Regeln
  • Label ist immer sichtbar, nie nur als Platzhalter.

    Platzhalter verschwinden beim Tippen und sind für Screenreader unzuverlässig.

    textfield/visible-label
  • Im Fehlerzustand ersetzt errorText den Hilfstext und erklärt, wie man den Fehler behebt.

    Rot allein sagt nicht, was zu tun ist.

    textfield/error-text
  • Aktionen im Feld (Passwort anzeigen, Eingabe leeren) nur über den Slot trailing, mit einem Button variant=ghost size=sm.

    Selbst über das Feld gelegte Knöpfe verlieren Fokusreihenfolge und Abstände.

    textfield/trailing-slot
  • Passwort anzeigen und Eingabe leeren kommen über trailingAction (reveal, clear), nicht über eigenes Skript.

    Nur so stimmen Beschriftung, aria-pressed und Fokus bei jedem Feld überein.

    textfield/trailing-behavior
Checkbox / 2 Regeln
  • Das Label ist Teil der Klickfläche.

    Die Box allein ist mit 20 px zu klein für Touch.

    checkbox/label-clickable
  • Ist die Checkbox deaktiviert, erklärt helperText den Grund.

    Ohne Erklärung wirkt ein deaktiviertes Element wie ein Fehler.

    checkbox/disabled-reason
Switch / 2 Regeln
  • Nur für Einstellungen, die sofort wirken. Braucht es Speichern, eine Checkbox verwenden.

    Ein Schalter verspricht, dass die Änderung schon gilt.

    switch/immediate
  • Ist der Schalter deaktiviert, erklärt helperText den Grund.

    Ohne Erklärung wirkt ein deaktiviertes Element wie ein Fehler.

    switch/disabled-reason
Chip / 2 Regeln
  • Höchstens zwei Wörter.

    Eine Filterzeile wird überflogen und soll in eine Zeile passen.

    chip/short-label
  • Nur zum Filtern oder Auswählen. Für Aktionen einen Button verwenden.

    Ein Chip bleibt gewählt, eine Aktion passiert einmal.

    chip/filter-only
Badge / 2 Regeln
  • Höchstens zwei Wörter.

    Badges werden überflogen, nicht gelesen.

    badge/short-label
  • Nie klickbar; für Filter einen Chip verwenden.

    Badges sehen nicht nach Bedienelement aus.

    badge/not-interactive
Alert / 3 Regeln
  • Höchstens ein Alert pro Bereich.

    Mehrere Hinweise übereinander werden ignoriert.

    alert/one-per-area
  • Titel nennt das Ergebnis, Beschreibung den nächsten Schritt.

    Man soll den Titel allein verstehen können.

    alert/title-states-outcome
  • Ein Alert enthält keine Aktion. Die Beschreibung nennt den nächsten Schritt, die Aktion steht dort, wo sie wirkt.

    Eine Aktion im Hinweis konkurriert mit der Hauptaktion der Seite.

    alert/no-action
Card / 3 Regeln
  • Höchstens eine Aktion im Footer.

    Karten sind Einstiege, keine Formulare.

    card/one-action
  • Keine Karten in Karten.

    Verschachtelte Rahmen zerstören die Hierarchie.

    card/no-nesting
  • Eine Kennzeichnung der Karte (z. B. „Aktuell“) gehört in den Slot badge, nicht daneben oder darüber.

    Nur im Slot bleibt die Kennzeichnung beim Umbruch an der Karte.

    card/badge-slot
Link / 2 Regeln
  • Der Linktext nennt das Ziel.

    „Hier“ oder „Mehr“ sagen nicht, wohin es geht, und sind in einer Linkliste nicht unterscheidbar.

    link/names-destination
  • Ein Link hat immer ein Ziel (href).

    Ohne Ziel ist er eine Aktion und gehört in einen Button.

    link/has-target
SignInForm / 1 Regel
  • Nur aus Systemkomponenten zusammensetzen.

    Muster zeigen Agenten und Menschen, wie Bausteine kombiniert werden.

    signinform/compose-from-system
ConfirmAction / 2 Regeln
  • Jede Aktion, die Daten unwiderruflich löscht, läuft über ConfirmAction.

    Ein roter Button allein schützt nicht vor einem versehentlichen Klick.

    confirmaction/for-irreversible
  • Das Freischalten kommt aus dem Muster, nicht aus eigenem Skript.

    Sonst unterscheiden sich Bestätigungen von Seite zu Seite.

    confirmaction/no-custom-script
